# UI internationalization

The UI supports English (`en`), Brazilian Portuguese (`pt-BR`), and neutral Latin American Spanish (`es`). English is the fallback. UI language does not select brand content language, generated content language, stored text, or Jaina report language.

## Phases

Phase 1 covers the application UI. Its production build, browser acceptance and performance qualification remain Phase 1 release requirements.

Phase 2 covers generated reports and narrative, exports and attachments, transactional/report emails, and other delivered system communications in all three locales. Report/output language and recipient delivery language remain independent of UI and brand content language. The cross-project scope is recorded in the monorepo's `docs/plans/i18n-phase-2.md`; Phase 2 implementation is planned.

## Routing and preferences

UI routes live under `src/app/[locale]`, with `localePrefix: 'never'`. Visible URLs stay unchanged. API routes and OAuth/auth callbacks remain outside that segment. The proxy composes the existing authentication behavior with locale rewrites and preserves query strings and return destinations. Anonymous shares do not perform authentication work.

The three locales have static parameters. `src/i18n/request.ts` reads Next.js 16.3 root parameters; ordinary translation reads do not introduce `cookies()` or `headers()` into cached page trees. Cache Components and partial prefetching remain enabled.

At sign-in, an existing account's valid `user_metadata.ui_locale` wins. Without one, the locale cookie, browser preference, then English determine the language. Ordinary navigation uses the cookie. Existing auth exchange/claims responses carry metadata; locale routing does not add a profile request. The validated `setUiLocaleAction` saves authenticated changes before changing the cookie. The selector refreshes only after success and retains the current language on failure.

With `localePrefix: 'never'`, navigation uses Next's existing `Link` and router. The pathname hook removes the internal locale segment when it appears during server rendering. `next-intl` continues to resolve locale routing and translations; the validated Server Action owns language changes. The selector uses the existing accessible radio primitives so authentication pages do not load a popup and its positioning/focus dependencies just to offer three languages.

## Catalog authoring and delivery

Canonical catalogs are `messages/<feature>/{en,pt-BR,es}.json`. `src/i18n/types.d.ts` derives typed keys from English. Use whole ICU messages for counts, interpolation, and rich text. Keep machine IDs, enum values, executable examples, currency codes, authored text, prompts, and source content separate from translated display labels.

`next-intl` is pinned at 4.15.0. Its build plugin compiles ICU messages ahead of time. Server components translate on the server. `FeatureMessages` sends source-derived key slices to client components. Existing client-only Library, presentation, and AI Studio boundaries load generated active-language catalogs alongside their code. These derived `messages/client-*` catalogs and `lazy-catalogs.generated.ts` are generated; edit their canonical sources instead.

Normal delivery uses one resolved UI locale. The server loads that locale's canonical catalogs; client providers receive only their selected feature keys, and each lazy editor invokes only its active-locale loader. Other languages remain separate build artifacts and are not proactively loaded. Switching language requests the newly selected locale; previously loaded modules may remain in the browser cache. Regression tests exercise all three languages at every lazy boundary and assert that inactive language and unrelated feature loaders are never invoked. The provider-independent global error screen is the narrow exception: its three emergency dictionaries total 412 bytes of source JSON, keeping recovery available if a provider or a chunk fails.

After changing a catalog, translation key, or client import, run from the Frontend:

```sh
bun run i18n:sync
bun run i18n:check
```

The scope generator follows runtime imports, literal key maps, finite template key families, translation namespace aliases, and client boundaries. It excludes server actions and stops eager delivery at declared lazy boundaries. Keep a new dynamic key family finite and typed; update the generator's behavior tests when introducing a new key construction pattern.

Google Cloud Translation is an offline authoring tool only. Source phrases and drafts are sealed under the approved i18n GCS run prefix. Drafts require context review before integration. Interpolation tokens are validated before restoring syntax; invalid drafts are rejected. No translation API, credentials, or runtime translation service is included in the app.

## Formatting and failures

Use active UI locale for dates, numbers, percentages, relative time, chart labels, calendars, and search labels. Preserve the original rounding, currency identity and scheduling timezone. Technical dates/timecodes and authored watermark templates retain their contract behavior. Display translation must never enter a stored ID, request parameter, comparison, or cache identity.

Use `useValidationErrorMap` per Zod parse/resolver for library-owned validation guidance. Keep schema constraints, custom validation rules and transformations unchanged; localize schema-owned messages through typed factories. The formatter uses stable issue codes and does not mutate Zod global configuration.

Media mention presentation uses structured kind/source/collection values; generated agent references and authored names/descriptions remain unchanged. Shared delta displays accept an explicit provider-free presentation so report language stays independent of UI language.

Use stable error codes and HTTP status for application guidance. Preserve diagnostic messages for debugging; unknown provider prose is not UI copy. Cross-project response changes belong in canonical contracts and the Frontend's standalone vendored copy. Public shares accept additive reason codes while retaining exact legacy-response compatibility. Global error rendering uses its own small dictionaries and works without normal providers.

## Checks and release evidence

`i18n:check` validates catalog completeness, ICU syntax, matching interpolation/rich-text arguments, generated scopes/catalog freshness, visible literals, notification helpers, authentication HTML, scoped constant/default bindings that reach display props, and translated machine values. It also rejects displaced client/server directives and checks rich callback bindings against catalog signatures. Literal exceptions name an exact file, text, kind and reviewed reason; stale exceptions fail. Focused tests use real catalogs and providers. Source checks cannot establish browser coverage or translation quality by themselves.

The Frontend production build runs `i18n:check`, `next typegen`, the existing typecheck, Next production build and existing bundle budgets. Type generation precedes typechecking so a fresh checkout validates the generated locale root parameters without relying on a previous dev/build directory. Locale route normalization keeps the previous visible-route budgets; no budget increase is implied.

The real-data browser/performance bench is at the monorepo root: `bun run i18n:e2e:bench`. Setup, private fixture configuration, source/build receipts and acceptance limits are documented in `scripts/i18n/README.md`. A green standalone production build and green real end-to-end evidence are required before deployment. Unit, type and catalog checks do not replace those gates.
